# GOODLE ↔ HNK-KODE / haKodan — Semantic Bridge V0.1

Status: absorbed as project knowledge / integration baseline
Source: tehknesolutions/HNK-KODE@main
Reviewed: 2026-09-29

## 1. Decision
Goodle does not become a second HNK-KODE runtime.
Goodle is a consumer/authoring surface that can project into the haKodan semantic model while preserving Goodle as the implementation source of truth.
Canonical relationship: GOODLE INTENT → GOODLE SEMANTIC IR → HNK-KODE / haKodan Semantic IDs → HNK-IR → manifestation.
The bridge is semantic, not a string-replacement layer.

## 2. What was absorbed
haKodan is the multicapa framework behind HNK-KODE. Its central transformation is INTENÇÃO → ESTRUTURA → PROGRAMA → EXECUÇÃO → MANIFESTAÇÃO.
Canonical ladder: L8 ALEF/INTENT → L7 NARRATIVE → L6 VISUAL/GLYPH/BLOCK → L5 HNK-KODE → L4 OBJECT/COMPONENT/TYPE → L3 SYSTEM/LOGIC/RUNTIME → L2 HNK-IR → L1 BYTECODE/TARGET IR → L0 BINARY/MALKUTH.
Goodle's existing intent → components → composition → rules → events → runtime → experience model fits this ladder naturally.

## 3. One semantic core
HNK-KODE defines HNK | PT-BR | EN as language surfaces converging on one Canonical AST and HNK-IR.
Goodle already uses semantic IDs rather than treating surface vocabulary as semantic authority. The bridge therefore resolves concepts, not translations.

## 4. Visual/text/glyph convergence
haKodan treats text, blocks, nodes and glyph/Mandala representations as projections of the same program/semantic identity.
Goodle Canvas/Nodes should therefore be an authoring projection of IR, not a separate programming language.

## 5. Provenance
Goodle IR already carries origem, termo and equivalencia. When HNK-KODE data is involved, preserve source repository, ref/version, semantic ID, authority state and source artifact.

## 6. MHCM boundary
MHCM is a computational projection/addressing model around TEXT ↔ AST ↔ MANDALA ↔ GLYPH ↔ HNK-IR. It does not create a second parser, semantic authority, IR or runtime beside haKodan.
Goodle should treat Mandala/Glyph as representation/authoring adapters, never as a competing runtime.

## 7. Authority/source-lock
HNK-KODE identifies CODEX-HNK as ROOT CANON and HNK-KODE as the linguistic Domain Canon.
Use states OBSERVED → DERIVED → HYPOTHESIS → CANDIDATE → VALIDATED → CANONICAL. UNRESOLVED means insufficient or conflicting evidence.
CANONICAL HNK lexemes may be consumed. DISCOVERY_NON_CANONICAL candidates remain provisional. Missing HNK lexemes remain unresolved. Goodle must never invent an HNK word to complete syntax.

## 8. Canonical HNK concepts currently safe to expose
AHNUVA = AMOR / LOVE / HNK-LG-0001
EMANU = VERDADE / TRUTH / HNK-LG-0002
HAYA = VIDA / LIFE / HNK-LG-0003
HODERU = CAMINHO / WAY / HNK-LG-0004
KODAN = LOGOS / LOGOS / HNK-LG-0005
These are semantic concepts, not automatically programming keywords.
The 127-entry KODIN registry contains additional terms, but the reviewed source marks the computational entries before these five as provisional/discovery-non-canonical. Goodle must not treat them as canonical HNK vocabulary.

## 9. Goodle ↔ haKodan correspondence
mundo → WORLD
entidade → ENTITY
propriedade → PROPERTY
evento → EVENT

quando → WHEN
intenção → INTENT
manifestar → MANIFEST
The HNK surface for a concept remains unresolved unless HNK-KODE has a confirmed canonical lexeme.

## 10. HNK constants in Goodle
AHNUVA, EMANU, HAYA, HODERU and KODAN should be semantic constants/knowledge references, not ordinary programming keywords.
Glyph IDs, sigil IDs, mathematical identity IDs, PUA code points and hashes remain source metadata from HNK-KODE and are not regenerated by Goodle.

## 11. Target/manifestation
haKodan separates semantic identity from targets. Therefore Goodle Semantic IR → target adapter, not Goodle → React semantics → HNK.
React, Phaser, Canvas, Web, Game and App remain manifestations/adapters.

## 12. GoodStudio implication
The authoring flow should become CommandBar → Intent → Semantic Nodes → Connections → Inspector → Goodle IR → Manifestation Plan → Runtime/Preview.
The Canvas is the visual authoring surface while the IR remains the semantic source.

## 13. First adapter
Build a versioned, read-only, evidence-preserving HNK-KODE Semantic Bridge:
1. Load the HNK-KODE registry ref/version.
2. Resolve only explicitly canonical HNK lexemes.
3. Resolve PT-BR/EN surface aliases through Semantic IDs.
4. Preserve source and authority metadata.
5. Reject invented HNK terms.
6. Validate equivalence into the same Goodle IR.
7. Expose HNK glyph metadata as an optional visual representation.
8. Keep MHCM as a representation/addressing adapter, not a parallel runtime.

## 14. Explicit non-goals
Do not copy the whole HNK-KODE repository into Goodle.
Do not treat every KODIN candidate as canonical.
Do not turn HNK-MATH geometry into vocabulary automatically.
Do not assign semantic or spiritual meaning to encoding surfaces merely because they exist.
Do not make Goodle dependent on a specific runtime target.

## 15. Immediate milestone
Create a versioned HNK-KODE Semantic Bridge with source manifest, canonical HNK registry subset, semantic-ID mapping, authority/provenance metadata, unresolved-token behavior, conformance tests for the five canonical concepts and optional glyph projection.

Core rule: semantic identity is upstream of language surface and target implementation.
